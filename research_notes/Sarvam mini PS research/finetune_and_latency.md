## Q1. Fine-tuning recipes and data formats of comparable open streaming S2S models

### Takeaway
The only complete, public, maintained recipe for a Hibiki/Moshi-class model is **kyutai-labs/moshi-finetune**. It uses LoRA r=128 with scaling 2, an unusually low LR of 2e-6, weight decay 0.1, 100 s windows, batch 16 and 2,000 steps. Data is stereo WAV (left channel = the model's output stream, right = the input stream) plus a per-file JSON `{"alignments": [[word, [start, end], "SPEAKER_MAIN"], ...]}` produced by whisper-timestamped. The PS's 80 ms / 3,840-byte frame equals exactly one Mimi codec frame (12.5 Hz at 24 kHz), and pairs must carry English word timings. Both point strongly to a Mimi-based, Hibiki-style decoder-only model with a time-aligned English text stream. So the best preparation is to build the pipeline for that format and keep it format-agnostic underneath.

### Cited Findings
- **moshi-finetune data format.** Stereo WAV, where "the left channel is used for the audio generated by moshi, whereas the second channel is used for the user's input". A `.jsonl` manifest has lines `{"path": ..., "duration": ...}`, and each WAV has a matching `.json` timestamped transcript — [moshi-finetune README](https://github.com/kyutai-labs/moshi-finetune)
- **Transcript JSON schema** (from the code; the README does not specify it): `{"alignments": [[word_text, (start, end), "SPEAKER_MAIN"], ...]}`. It is written by `annotate.py` using `whisper_timestamped` with `beam_size=5, best_of=5`, a temperature fallback of (0.0…1.0), and auditok VAD for clips over 10 s. The help text says "use medium for stereo" and warns against large-v3 without VAD — [annotate.py](https://github.com/kyutai-labs/moshi-finetune/blob/main/annotate.py)
- **Example config** (`moshi_7B.yaml`): `full_finetuning: false`, `lora.rank: 128`, `lora.scaling: 2.`, `ft_embed: false`, `first_codebook_weight_multiplier: 100.`, `text_padding_weight: .5`, `duration_sec: 100`, `batch_size: 16`, `max_steps: 2000`, `gradient_checkpointing: true`, `optim.lr: 2e-6`, `weight_decay: 0.1`, `pct_start: 0.05` (OneCycle warm-up), `eval_freq: 100`, `ckpt_freq: 100`, `save_adapters: true` — [moshi_7B.yaml](https://github.com/kyutai-labs/moshi-finetune/blob/main/example/moshi_7B.yaml). The README says LR "Recommended starting value: 2e-6", LoRA rank "≤128 for efficiency", and that its training-curve figure used a max LR of 4e-6 — [README](https://github.com/kyutai-labs/moshi-finetune)
- **Loss.** Separate text and audio cross-entropy terms are summed (`mb_loss = text_loss + audio_loss`). Text PAD/EPAD tokens are down-weighted by `text_padding_weight`, and codebook 0 (the semantic codebook) is up-weighted by `first_codebook_weight_multiplier` — [train.py](https://github.com/kyutai-labs/moshi-finetune/blob/main/train.py), [loss.py](https://github.com/kyutai-labs/moshi-finetune/blob/main/finetune/loss.py). The code defaults are 1.0 and 0.5 — [args.py](https://github.com/kyutai-labs/moshi-finetune/blob/main/finetune/args.py)
- **Interleaver.** It converts word alignments into a 12.5 Hz text stream of word tokens, PAD and END-OF-PADDING (EPAD, placed in the frame before a word). It has an `audio_delay` parameter (a text-vs-audio shift, default 0.0) and a `keep_main_only` option — [interleaver.py](https://github.com/kyutai-labs/moshi-finetune/blob/main/finetune/data/interleaver.py)
- **Conditioning.** The training loop passes `condition_attributes` through `model.condition_provider`. This is the hook a Hibiki-style quality-label conditioning would need — [train.py](https://github.com/kyutai-labs/moshi-finetune/blob/main/train.py)
- **Infrastructure.** FSDP with a separate LoRA wrap policy, bf16 `param_dtype` with upcast for the optimizer step, and `torchrun` even on one GPU. Measured throughput is ≈12k tokens/s on 1×H100 (peak 39.6 GB) and ≈10.7k tokens/s on 8×H100 (23.7 GB). The token formula is `max_steps × num_gpus × batch_size × duration_sec × 9 × 12.5`. Inference with an adapter uses `python -m moshi.server --lora-weight=... --config-path=...` — [README](https://github.com/kyutai-labs/moshi-finetune), [wrapped_model.py](https://github.com/kyutai-labs/moshi-finetune/blob/main/finetune/wrapped_model.py)
- **README warning.** "Lowering `duration_sec` may make the model go silent sooner during inference". The training window length therefore affects long-session behaviour — [README](https://github.com/kyutai-labs/moshi-finetune)
- **Moshi 7B architecture constants.** Temporal transformer dim 4096, 32 layers, 32 heads, text vocabulary 32,000, `n_q` 16 total audio codebooks with `dep_q` 8 generated, and a depth transformer of dim 1024 with 6 layers. Mimi runs at `frame_rate: 12.5` — [loaders.py](https://github.com/kyutai-labs/moshi/blob/main/moshi/moshi/models/loaders.py). Moshi's theoretical latency is "160ms (80ms for the frame size of Mimi + 80ms of acoustic delay)", with 200 ms in practice on an L4 — [moshi README](https://github.com/kyutai-labs/moshi/blob/main/README.md)
- **Hibiki.** A 2B model with 16 RVQ per stream and a 1B variant with 8 RVQ. It runs at a 12.5 Hz constant frame rate for text and audio, uses "simple temperature sampling", has a 40 s context, and was trained on sequences up to 120 s. Its synthetic data uses "contextual alignment" with MADLAD plus silence insertion or alignment-aware TTS — [hibiki README](https://github.com/kyutai-labs/hibiki)
- **Hibiki paper.** Word-level delays are scored by how the perplexity of an off-the-shelf MT model changes as the source is truncated (contextual alignment). Training data is synthetic, made by translating and re-synthesising monolingual transcripts. Hibiki outperforms Seamless/StreamSpeech "at the cost of an average 0.7s of additional lagging" — [arXiv 2502.03382 via HF papers](https://huggingface.co/papers/2502.03382) (search summary)
- **Hibiki-Zero (Feb 2026, ICML 2026).** A 3B model trained without word-level alignments. Stage 1 is supervised on sentence-level aligned data, producing a high-latency model. Stage 2 is GRPO RL with a BLEU-based reward (reportedly computed at intermediate points, without KL) to cut latency. It is claimed to adapt to a new input language with <1000 h — [arXiv 2602.11072](https://arxiv.org/html/2602.11072v1), [ICML oral page](https://icml.cc/virtual/2026/oral/71089) (search summary). The repo says it is 3B and "8 GB VRAM should work, 12 GB is safe", and its inference code is built on the `moshi` package (LMGen, loaders) — [hibiki-zero README / inference.py](https://github.com/kyutai-labs/hibiki-zero). The weights are CC BY-NC-SA 4.0 — [HF model card](https://huggingface.co/kyutai/hibiki-zero-3b-pytorch-bf16) (search summary)
- **StreamSpeech.** Jointly learns translation and the simultaneous read/write policy in one multi-task framework (ASR, ST and TTS heads; ACL 2024). It is a different, CTC-policy, non-LM architecture — [arXiv 2406.03049](https://arxiv.org/html/2406.03049) (search summary)

### Inferences
- **Architecture guess.** 3,840 bytes = 1,920 samples = 80 ms at 24 kHz, which is exactly Mimi's frame (24000/12.5). Combined with "trained on synthetic data" (Hibiki's recipe) and "needs English word timings" (the Moshi interleaver's text stream), the most probable base is a Hibiki/Hibiki-Zero-like Mimi + temporal transformer + depth transformer model with an English inner-monologue text stream. Plausible sizes range from ~1B to ~7B. Plan for Moshi-style stereo + alignment JSON, but keep the canonical store neutral (see Q2) so a non-Moshi layout costs only a converter.
- **LR.** moshi-finetune's 2e-6 LR is about 50–100× below typical LoRA LRs (1e-4 to 2e-4). That suggests Kyutai found Moshi fragile. Start there and sweep upward (2e-6, 1e-5, 5e-5) only with early stopping.
- **Rehearsal model.** Hibiki-Zero 3B is the best rehearsal proxy. It is public, built on the same `moshi` library that moshi-finetune trains, small enough for cheap runs, and explicitly claimed to adapt to new input languages. Fine-tuning it on ~10–20 h of our Hindi→English pairs before the mid-term exercises the whole pipeline: stereo construction, alignment JSON, LoRA, eval harness, WebSocket server. The non-commercial licence fits practice use. The rehearsal checkpoint is never submitted.
- **Out of scope.** Qwen2.5-Omni, Kimi-Audio, GLM-4-Voice, Mini-Omni, LLaMA-Omni, Freeze-Omni and Sesame CSM are turn-based (non-simultaneous) or TTS-only. Their recipes (mostly speech-adapter + LLM SFT) are less relevant to a full-duplex simultaneous model. They were not researched in depth here.

### Gaps
- I could not fetch the Hibiki or Hibiki-Zero PDFs, so stage-by-stage hours, steps, LR, batch and GRPO hyperparameters (group size, reward schedule) are unverified. Hibiki's ASR-BLEU is reported inconsistently by secondary sources (30.5 vs 39.2), probably from different test sets. Verify on the PDF.
- I found no public fine-tuning recipes for SeamlessStreaming or for Sesame CSM.
- I did not confirm whether moshi-finetune loads Hibiki/Hibiki-Zero checkpoints directly. It defaults to `kyutai/moshiko-pytorch-bf16`; condition-provider plumbing exists, but loading hibiki was not tested.

## Q2. Architecture-agnostic infrastructure to build before the mid-term

### Takeaway
Build a **neutral pair store plus thin exporters**, an **alignment and QA pipeline**, an **eval harness that replays the exact WebSocket protocol on a playback timeline**, and a **rehearsal fine-tune on Hibiki-Zero**. These carry over to any architecture. Design decisions that depend on the model (tokenizer, delay pattern, conditioning labels) should be parameters, not code.

### Cited Findings
- External models are allowed during training for alignment, reward models and teachers. Only the submitted system is cascade-restricted — Sarvam PS §11 FAQ (local `/home/user/interiit_minips/Sarvam.pdf`)
- Augmented copies (noise, speed, reverb) applied during training add no hours — Sarvam PS §3 Part A
- After the mid-term, existing records may be improved but not added — Sarvam PS §3 Part B
- The Moshi target format is stereo WAV plus `alignments` JSON, annotated with whisper-timestamped — [annotate.py](https://github.com/kyutai-labs/moshi-finetune/blob/main/annotate.py)
- Hibiki builds the source↔target timing with "contextual alignment" (MT-perplexity-based word delays) and either silence insertion or alignment-aware TTS — [hibiki README](https://github.com/kyutai-labs/hibiki)
- Hibiki-Zero needs only sentence-level alignment, "easily obtained from punctuation", and then relies on RL for latency — [arXiv 2602.11072](https://arxiv.org/html/2602.11072v1) (search summary)
- Hibiki inference signals end of input by feeding one frame with all codebooks = `mimi.cardinality` (2048), then Mimi-encoded silence, and stops when the text stream emits EOS. It warns "EOS sampled too early" if EOS appears before input end — [run_inference.py](https://github.com/kyutai-labs/moshi/blob/main/moshi/moshi/run_inference.py). Hibiki-Zero's `add_input_eos` puts the EOS frame at `ceil(duration × frame_rate)` and trims output audio at the text EOS index — [hibiki-zero inference.py](https://github.com/kyutai-labs/hibiki-zero)
- ATD is computed in SimulEval by treating 300 ms speech segments as tokens. The NAIST IWSLT 2024 system reports ATD + StartOffset + EndOffset, with ASR-BLEU using Whisper — [ATD arXiv 2211.13173](https://ar5iv.labs.arxiv.org/html/2211.13173), [NAIST arXiv 2407.00826](https://arxiv.org/pdf/2407.00826) (search summary); SimulEval toolkit — [arXiv 2007.16193](https://ar5iv.arxiv.org/html/2007.16193)

### Inferences
Prioritised build list. Each item is cheap and model-agnostic.
1. **Canonical pair store** (Parquet/JSONL). Per sentence and per record it holds: Hindi wav path, `hi_words` (already required in Part A), Bulbul English wav per (pace, temperature) variant, English word timings, a Hindi↔English word/phrase alignment, entity spans (numbers, amounts, dates, names, phone/account digits) with their Hindi and English positions, a speaker id, and a train/dev split. Exporters are thin: (a) Moshi/Hibiki stereo (L = English target placed on the Hindi timeline, R = Hindi) plus `alignments` JSON; (b) generic `(src_wav, tgt_wav, tgt_words[], src_words[])` tensors for any other layout.
2. **Placement engine (the key latency lever).** This builds the time-aligned English track. For each English word, compute the earliest Hindi time at which it is "safe" (contextual alignment: the Hindi prefix length at which an MT model's confidence in that English word saturates; an LLM or MT model is allowed as a training-time teacher). Then place Bulbul audio with inserted silences so that each English word starts no earlier than safe_time + margin. Expose margin, per-entity extra wait, and Bulbul pace as knobs, so several lag regimes (for example ~1.5 s, 2.5 s, 3.5 s mean lag) can be generated from the same records after the mid-term. Re-synthesising per sentence is allowed because pace is free, but it must be declared.
3. **English forced alignment and QA.** Run CTC forced alignment (for example wav2vec2/MMS or the WhisperX aligner) on Bulbul output against the known English text. This is more reliable than free ASR timestamps because the text is known. Then run a Whisper ASR round-trip to flag skipped or repeated words and misspoken numbers or names, and regenerate failures, as the PS requires. Enforce timings that are ordered, non-negative and inside the clip.
4. **Eval harness.** This should be a faithful replay of the harness: send 80 ms frames in real time; after input_end, send silence; reconstruct the *playback timeline* (a frame starts at max(arrival, previous end)). Compute StartOffset, EndOffset, ATD and LAAL-style word lags by force-aligning the ASR transcript of the output to time and mapping it to Hindi `hi_words` via the pair alignment. Quality metrics: ASR-BLEU / chrF / COMET on the output ASR; entity exact-match with number normalisation (25,000 ≡ 25k ≡ "twenty-five thousand"; keep lakh/crore units); an intent and negation check with an LLM judge (allowed offline for eval); and UTMOS-style audio quality. Also enforce the failure rules (reads within 1 s, session_complete within 30 s, nothing after it).
5. **Reference WebSocket server skeleton.** Use an asyncio reader that never blocks on the GPU (a reader task feeding a queue, a GPU thread doing step(), and a sender task). Include a watchdog and health endpoint, a forced flush path on input_end, and per-step timing logs. The model step becomes a plug-in.
6. **Training scaffolding.** Include PEFT-style LoRA injection by module-name regex, bf16 + FSDP/ZeRO-2, gradient checkpointing, OneCycle, an eval-every-N-steps hook into the harness, adapter merge/export to safetensors, and Modal job wrappers with checkpoints on a Modal Volume so pre-emptions or timeouts lose nothing.
7. **Rehearsal.** Fine-tune Hibiki-Zero 3B (or Hibiki 1B) on ~10–20 h of our pairs, end to end, and measure base-vs-fine-tuned on a speaker-disjoint real-Hindi dev set.

### Gaps
- No source shows how Sarvam computes its latency KPI, specifically how output words are timed and matched to Hindi words, and how "trailing" and "finishing" are combined. The harness above has to guess the metric.

## Q3. Risks of small-data fine-tuning, mitigations, and compute/budget

### Takeaway
The main risks are: degrading the base's **latency behaviour** (if our English placement lags more than the base's training data, fine-tuning teaches it to wait longer); **forgetting** general translation; **overfitting** to the few real Hindi speakers in Part A; and a mismatch between the pause and stretch patterns of **Bulbul pace** and the base's own targets. LoRA on a 2–7B model over ~100–200 h is cheap: about 2 H100-hours per epoch of 200 h on a 7B Moshi, roughly $8 per epoch. The budget therefore supports dozens of runs. The real limits are evaluation time and iteration count, not GPU-hours.

### Cited Findings
- **Throughput.** ≈12k tokens/s on 1×H100 for Moshi 7B LoRA, peak 39.6 GB, with tokens = steps × GPUs × batch × duration_sec × 9 × 12.5 — [moshi-finetune README](https://github.com/kyutai-labs/moshi-finetune)
- **Recommended quick run.** 2000 steps × batch 16 × 100 s — [moshi_7B.yaml](https://github.com/kyutai-labs/moshi-finetune/blob/main/example/moshi_7B.yaml)
- **Modal H100 price.** Third-party trackers list $0.001097/s ≈ $3.95/h (down from $0.001644/s in late 2024 and $0.001267/s in Jan 2025) — [Spheron blog](https://www.spheron.network/blog/modal-gpu-pricing-2026-per-second-billing/), [usagepricing calculator](https://usagepricing.com/tools/pricing-calculator/modal), [pricingsaas 2025Q1 diff](https://pricingsaas.com/companies/modal/diffs/2025Q1) (search summary; modal.com/pricing itself could not be fetched)
- **LoRA.** Freezes base weights and trains low-rank updates, cutting trainable parameters by up to 10,000× on GPT-3 with comparable quality — [arXiv 2106.09685](https://arxiv.org/abs/2106.09685) (abstract, not re-fetched). Moshi's own LoRA replaces *all* Linear layers (`replace_all_linear_with_lora`) — [moshi lora.py](https://github.com/kyutai-labs/moshi/blob/main/moshi/moshi/modules/lora.py)
- moshi-finetune weights codebook 0 by ×100 and text padding by ×0.5 in its example config. This is a choice about which tokens the loss attends to — [moshi_7B.yaml](https://github.com/kyutai-labs/moshi-finetune/blob/main/example/moshi_7B.yaml)
- A shorter `duration_sec` can make the model go silent sooner at inference — [README](https://github.com/kyutai-labs/moshi-finetune)
- Only Part A data may be used for training, and English targets in supervised pairs must be Bulbul shubh. External teachers and reward models are allowed during training — Sarvam PS §3 Part B and §11

### Inferences
- **Compute arithmetic** (assuming the 12k tok/s figure is per GPU): 12,000 / (9 × 12.5) ≈ 107 audio-seconds per wall-second. One epoch of 200 h (720k s) takes ≈ 6,750 s ≈ 1.9 H100-h ≈ $7.4. The recommended 2000×16×100 s run is 3.2M audio-s (≈ 889 h, ≈ 4.4 epochs of 200 h) and takes ≈ 8.3 h ≈ $33. A 2–3B base should be about 2–3× cheaper. $1,000 at $3.95/h is ≈ 253 H100-h total, but some credits arrive before the mid-term and get spent on data. If ~$700 remains after the mid-term, that is ≈ 175 H100-h: roughly 15–20 LoRA runs plus eval. Eval is real-time-bound (a 60 s session takes ≥ 60 s), so parallelise eval across containers.
- **Full fine-tuning memory.** A 7B model with Adam needs ~16 bytes/param (bf16 weights + grads + fp32 master + 2 moments), about 112 GB. That does not fit on one 80 GB H100, so it needs FSDP over ≥ 2 GPUs or 8-bit optimisers. A 2–3B model fits on one H100. Prefer LoRA first. Use full fine-tuning only if LoRA plateaus and the base is small.
- **Mitigations, ranked.**
  - (1) Measure the base's own lag distribution on our dev set first (run the base, align its output) and generate placement-engine pairs that match or slightly beat it. Do not let fine-tuning drift later.
  - (2) LoRA r 16–64 on the temporal transformer only. Freeze Mimi always, and freeze the depth transformer at first (audio quality is only 6 pts and the base already speaks shubh-like English).
  - (3) Low LR (2e-6 to 1e-5), short runs, and early stopping on the speaker-disjoint real-Hindi dev set, scored by our harness (entity, intent, lag), not by loss.
  - (4) Heavy input-side augmentation (noise, telephone band-limiting/codecs, reverb, speed, gain), which adds no hours and targets the hidden test's "background noise and telephone audio".
  - (5) A regulariser toward the base: a KL term between the fine-tuned and frozen-base logits on Part A inputs (base as "teacher", allowed during training). This stands in for the replay data that cannot be used.
  - (6) Mix lag regimes, and if the base has a lag or quality conditioning, keep its labels consistent.
- **Upweight entity tokens.** moshi-finetune's text_padding_weight shows the loss can be token-weighted. Extend this to upweight text tokens inside entity spans (numbers, amounts, names) for a cheap entity-accuracy gain.
- **RL option.** If time allows, a Hibiki-Zero-style GRPO stage is permitted, with reward models allowed during training. The reward would be a BLEU/entity-match score on ASR of rollouts minus a lag penalty. This stage is costlier and riskier, so treat it as a stretch goal.

### Gaps
- The Modal H100 price was not verified on modal.com (fetch blocked). Third-party sources agree on $3.95/h. Confirm in the Modal dashboard.
- It is unknown whether the base was trained with the shubh voice. If it was not, fine-tuning on shubh-only targets changes the voice, which may help or hurt audio-quality ratings.
- No source quantifies forgetting for LoRA vs full fine-tuning on Moshi-class models.

## Q4. Decoding-time choices: lag vs entity accuracy

### Takeaway
For a Moshi/Hibiki-style model, lag is mostly baked in by training-data placement. Decoding knobs give fine control on top. The highest-value, low-risk choices are:
- **Exact input-EOS handling plus a fast flush after input_end**, and a mild word-preserving time-stretch of backlog audio, both for EndOffset.
- **A text-stream PAD/EPAD logit bias** for trailing lag, gated off around unfinished numbers and entities.
- **Lower text temperature or top-k** for entity accuracy.

CFG, quantisation and speculative decoding mainly trade compute. On an H100 a ≤7B model already runs well within the 80 ms per frame budget, so they are not latency levers. If CFG is used at all, use it for audio quality.

### Cited Findings
- **Moshi `LMGen` defaults.** `temp=0.8` and `top_k=250` (audio), `temp_text=0.7` and `top_k_text=25` (text), `cfg_coef=1.`. Separate text and audio sampling parameters are supported, and top-p is supported in `sample_token` — [lm.py](https://github.com/kyutai-labs/moshi/blob/main/moshi/moshi/models/lm.py), [sampling.py](https://github.com/kyutai-labs/moshi/blob/main/moshi/moshi/utils/sampling.py). Checkpoints can ship their own `lm_gen_config` defaults — [loaders.py](https://github.com/kyutai-labs/moshi/blob/main/moshi/moshi/models/loaders.py)
- **Forced tokens.** `LMModel` has `text_padding_token_id`, `end_of_text_padding_id` and an `ungenerated_token_id` that "allows for partial teacher forcing, by generating one modality, with the other one fixed". This means PAD/EPAD can be forced or biased in the text stream from decoding logic — [lm.py](https://github.com/kyutai-labs/moshi/blob/main/moshi/moshi/models/lm.py)
- **Hibiki CFG.** Conditioning is a text "description" of `very_good`, with `very_bad` as the CFG negative — [run_inference.py](https://github.com/kyutai-labs/moshi/blob/main/moshi/moshi/run_inference.py). The README says: "the higher the value, the closer the generated voice should be to the original voice", typical value 3, but "excessive coefficients can lead to worse translations" — [hibiki README](https://github.com/kyutai-labs/hibiki). Hibiki-Zero's real-time path builds `LMGen(lm, cfg_coef=1, ...)`, so its server uses no CFG — [hibiki-zero inference.py](https://github.com/kyutai-labs/hibiki-zero)
- Hibiki is "compatible with batching" because it uses simple temperature sampling — [hibiki README](https://github.com/kyutai-labs/hibiki)
- **End of input.** Hibiki feeds an EOS input frame (codes = 2048), then silence, and stops on text EOS — [run_inference.py](https://github.com/kyutai-labs/moshi/blob/main/moshi/moshi/run_inference.py)
- **Quantisation.** Moshi's PyTorch int8 path is bitsandbytes vector-wise int8 (`QLinear`), and the PyTorch q8 checkpoints are labelled "(experimental)" — [quantize.py](https://github.com/kyutai-labs/moshi/blob/main/moshi/moshi/utils/quantize.py), [moshi README](https://github.com/kyutai-labs/moshi/blob/main/README.md)
- **CUDA graphs and compile.** The moshi codebase already uses `CUDAGraphed` (streaming exec mask, Mimi) and `torch_compile_lazy` (transformer, RoPE, gating) — [moshi repo](https://github.com/kyutai-labs/moshi) (grep of `moshi/moshi/modules/*.py`, `models/compression.py`)
- **Speculative decoding.** It gives 2–3× speedups with output distribution identical to the target model — [arXiv 2211.17192](https://arxiv.org/abs/2211.17192) (abstract, not re-fetched). For codec LMs, multi-token prediction heads plus speculative/Viterbi decoding cut per-token time ~4–5× — [arXiv 2410.13839](https://arxiv.org/html/2410.13839v1) (search summary). Coarse-grained acceptance for speech speculative decoding is proposed in [arXiv 2511.13732](https://arxiv.org/pdf/2511.13732) (search summary). NVIDIA speculates over the multi-codebook "CodePredictor" inner loop using per-depth heads the checkpoint already has, with no separate draft model — [TensorRT-Edge-LLM docs](https://nvidia.github.io/TensorRT-Edge-LLM/user_guide/features/codepredictor-speculative-decoding.html) (search summary)
- **Entities vs latency.** I found no study that directly measures entity or number accuracy as a function of latency in SimulST/S2ST. The closest is a 2026 terminology-adaptation paper reporting named-entity recall across latency operating points — [arXiv 2607.17766](https://arxiv.org/pdf/2607.17766) (search summary) — and FBK's DireSTI project targeting NE/term/number accuracy in simultaneous ST — [FBK DireSTI](https://mt.fbk.eu/diresti/)
- **Playback rule.** A frame starts at max(arrival, previous end), so gaps are heard as silence. Speech after the speaker stops counts toward latency. Post-processing that doesn't change words (loudness, silence trimming) is allowed. Filler or padding speech is banned — Sarvam PS §5.1 and §10

### Inferences
Concrete recommendations, cheapest first:
1. **End-of-input flush (EndOffset).** On `input_end`, use `valid_samples` to find the exact last real frame. If the base accepts an EOS input marker (Hibiki-style), inject it there. Then stop waiting for the harness's real-time silence frames: feed synthetic silence internally and run model steps as fast as the GPU allows until text EOS. Stream the audio immediately (frames of ≤ 1 s). Generation-time stall then disappears, and EndOffset ≈ the remaining unspoken content.
2. **Backlog-aware time-stretch and silence trimming (AL and EndOffset).** Track the gap between generated audio and the playback clock. When audio is queued behind earlier audio, trim internal pauses longer than ~250 ms and apply a WSOLA/phase-vocoder speed-up of about 1.05–1.2×, which preserves the words. Do not stretch when there is no backlog, because it gains nothing on the playback timeline and costs audio quality.
3. **Bulbul pace in the training targets.** A slightly faster pace (for example 1.1) shortens English and reduces lag build-up at the source. This is a training-data knob that must be declared, and it is cheaper in quality terms than post-hoc stretch.
4. **PAD/EPAD logit bias (trailing lag).** Subtract β from the PAD logit to speak earlier, or add to it to wait. Sweep β on the dev set and plot lag against entity, intent and BLEU. Gate the bias:
   - (a) set β = 0 (or add wait) while the last Hindi words are a number or number-multiplier not yet closed (हज़ार, लाख, करोड़, सौ, digit strings), or while the clause verb has not arrived and negation is undecided;
   - (b) only allow earlier emission when the top non-PAD token's probability is high.
   This uses only the checkpoint's own logits, so it is decoding logic, not a cascade. A lightweight streaming Hindi *number-word detector* on the input would be "a component outside the checkpoint that produces Hindi text from the input audio" used to steer, which is likely a cascade violation. Gate on the model's own text-stream state and entropy instead.
5. **Text temperature (entity accuracy).** Go lower than the default 0.7, or use top-k 1–5 in entity contexts, keeping audio temp ~0.8. Watch for degenerate PAD loops, where greedy text can stall. Increase the temperature again only if output goes silent.
6. **Self-consistency wait (an internal stabiliser).** Run B parallel samples of the text stream (batch dimension, sharing the same input). Allow committing a new word only when ≥ k of B agree, otherwise force PAD. This costs B× compute, which is fine on an H100 for a 2–3B model. It adds lag only where the model is uncertain, which is exactly where entities and verbs go wrong.
7. **CFG.** Test it only as an audio-quality knob (γ 1.5–3) if the base has quality conditioning. It doubles compute and can hurt translation, per the Hibiki README. Keep γ = 1 if it costs entity accuracy.
8. **Speed engineering.** Use bf16, CUDA graphs and torch.compile, and keep a single static KV cache sized to 60 s plus a tail. Avoid int8/fp8 unless the per-step time exceeds ~60 ms, because quantisation risks rare-token (entity) errors for no latency gain. Speculative decoding (temporal steps cannot be drafted past unseen input; depth-transformer codebooks can be drafted by self-heads) is worth it only if the base plus CFG or self-consistency busts the 80 ms budget.
9. **Beam search.** True beam search is incompatible with no take-backs: audio follows text within ~1–2 frames (Moshi's acoustic delay is 80 ms). Only a lookahead of L frames is possible, and it adds L × 80 ms of lag. Prefer #6.

### Gaps
- There is no empirical evidence, for any Moshi-class model, on how PAD bias trades lag against entity or number accuracy. This has to be measured with our own sweep.
- It is unknown whether the base exposes lag or quality conditioning, an input-EOS token, or an acoustic delay. The inference code is released only after the mid-term.

## Q5. Why local agreement and re-translation are not usable (except as internal stabilisation)

### Takeaway
Re-translation revises earlier output, and LocalAgreement commits only the prefix that consecutive re-decodes agree on. Both assume (a) output can be withheld cheaply while the full prefix is re-decoded, and (b) for re-translation, that output can be revised. Spoken output is final and plays on a sequential timeline. In an end-to-end streaming S2S model the audio is generated *with* the text at every 80 ms frame, so neither can be used as an output policy. The agreement idea survives only internally: as a gate on when to let the model emit (Q4 #6) or as a training-time tool for building safe word placements.

### Cited Findings
- Whisper-Streaming uses LocalAgreement-n, emitting the longest common prefix of n consecutive hypotheses over a growing buffer, with ~3.3 s latency on long-form ASR — [arXiv 2307.14743](https://arxiv.org/abs/2307.14743) (abstract, not re-fetched)
- "No take-backs. Audio, once sent, is final." The harness plays frames in order received — Sarvam PS §5.1
- In Hibiki/Moshi the text token and the audio codebooks are produced in the same step (with a small acoustic delay), so withholding speech means forcing PAD and silence into the model's own stream — [lm.py](https://github.com/kyutai-labs/moshi/blob/main/moshi/moshi/models/lm.py), [moshi README](https://github.com/kyutai-labs/moshi/blob/main/README.md)

### Inferences
- **Re-translation** needs revisions (impossible here) and re-runs the model on the growing source each step, which is O(n²) compute and breaks the streaming state of a duplex model.
- **LocalAgreement as output policy** needs a separate TTS to speak committed text, which is a cascade. In-checkpoint, the equivalent is parallel sampled continuations of the text stream with commit on agreement, which is allowed decoding logic. This is the self-consistency wait in Q4.
- **Training time.** Agreement or MT-prefix-confidence over Hindi prefixes is a good way to compute each English word's earliest safe time for the placement engine (Hibiki's contextual alignment uses the same idea with perplexity).

### Gaps
- No source evaluates LocalAgreement-style gating inside a full-duplex S2S LM.

## Q6. Likely latency metrics and which knobs move each

### Takeaway
The KPI wording ("how far the English speech trails the speaker, and how soon it finishes after the speaker stops") maps to a **trailing-lag metric** (ATD, or an AL/LAAL computed on time-aligned output words vs Hindi word times) plus **EndOffset**. Possibly **StartOffset** is included too. Training-data placement moves all of them most. The EOS flush and stretch move EndOffset. PAD bias moves trailing lag and StartOffset. Compute speed matters only if steps exceed 80 ms.

### Cited Findings
- SimulEval provides AL, AP and DAL, and ATD is implemented there. For speech output, ATD treats 300 ms segments as tokens — [arXiv 2007.16193](https://ar5iv.arxiv.org/html/2007.16193), [arXiv 2211.13173](https://ar5iv.labs.arxiv.org/html/2211.13173) (search summary)
- IWSLT S2ST evaluations report ATD, StartOffset and EndOffset (Agarwal et al., 2023) with Whisper ASR-BLEU — [NAIST arXiv 2407.00826](https://arxiv.org/pdf/2407.00826) (search summary)
- Hibiki trades about 0.7 s of extra average lag for higher quality than Seamless/StreamSpeech — [arXiv 2502.03382](https://huggingface.co/papers/2502.03382) (search summary)
- The Part A format already requires Hindi word-level timings for every word, which an organiser could pair with output-word timings — Sarvam PS §5.2
- Timing is measured on the playback timeline, and speech after the speaker stops counts — Sarvam PS §5.1

### Inferences
| Metric | Main movers | Secondary |
|---|---|---|
| StartOffset (first output speech − source start) | placement margin for the first words; PAD bias at the session start | warm-up (Hibiki-Zero skips the first input frame); server accept and first-step time |
| ATD / AL / LAAL (trailing lag) | training lag regime; PAD/EPAD bias; Bulbul pace | backlog trimming and stretch; self-consistency gate (adds lag where uncertain) |
| EndOffset (output end − input end; the PS's "finish") | EOS-at-valid_samples plus flush faster than real time; tail stretch and pause trimming | pace; avoiding long trailing silence before EOS |
| Compute lag (step > 80 ms builds backlog) | CUDA graphs and compile; no CFG; bf16 | int8/fp8; speculative decoding of depth codebooks |

- **Scorer integrity.** Never emit filler to lower StartOffset, because it is banned.
- **Silent frames.** On the playback timeline, sending silent frames and sending nothing are equivalent, except when audio is queued behind them.

No source answers this, and the PS gives only prose.
